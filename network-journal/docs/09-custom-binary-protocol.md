# 09 · 自定义二进制协议：定界与字段还原

> 一句话：TCP 只给你一条连续字节流，**消息边界必须由应用协议自己定义**；自定义协议的逆向，就是先找出「怎么切」，再还原「每一段是什么」。

## 是什么 / 为什么重要

很多协议不是 HTTP 这种文本协议，而是游戏、物联网、金融行情、私有 RPC 常用的自定义二进制格式。它们的共同点是：

- 头部有固定结构（魔数、版本、命令、长度、序号、校验和）；
- 载荷用 TLV 或固定字段排列；
- 长度字段的**口径**（算不算头、算不算自己）不写在文档里，只能靠样本验证。

这也是抓包分析最容易被卡住的地方：Wireshark 能帮你把 TCP 流重组成字节，但**认不出业务消息边界**，除非你告诉它（或用 Lua 插件）。所以「粘包/半包」不是网络故障，是协议设计要解决的问题。

## 机制与结构

### 1. 三种定界方式

| 方式 | 怎么切 | 优点 | 缺点 | 典型协议 |
|:---:|---|---|---|---|
| 定长 | 每条消息固定 N 字节 | 实现最简单 | 长度不能变，浪费带宽 | 某些传感器帧 |
| 分隔符 | 用特殊字节/字符串结尾 | 可读性好 | 分隔符要在载荷里转义 | 行协议、Redis 的部分格式 |
| 长度字段 | 头部写明长度，先读头再读体 | 高效、可嵌套 | 需要处理半包 | 绝大多数二进制协议 |
| TLV | Type + Length + Value 逐项解析 | 可扩展、可跳过未知字段 | 每项有 2 字节以上开销 | Protobuf 的变体、私有协议 |

真实协议经常是组合：**外层长度字段 + 内层 TLV**。

### 2. 一个可复现的协议格式

本仓库的 [`tools/frame-demo.py`](../tools/frame-demo.py) 用下面这个格式：

```text
 偏移  长度  字段        说明
 0     2     magic       固定 4e 50（"NP"），用来快速识别协议
 2     1     version     协议版本，便于灰度升级
 3     1     cmd         命令字，决定 body 怎么解释
 4     1     flags       位标志，如压缩、加密、应答
 5     2     seq         序号，用于请求/响应配对
 7     4     body_len    body 的字节数（大端，只算 body）
 11    2     checksum    16 位校验和，覆盖 header + body
 13    n     body        TLV 序列：Type(1) + Length(1) + Value(Length)
```

一条真实帧（`cmd=0x01`、`seq=1`、body 是 `alice` 和 `18` 两个字段）：

```text
0000  4e 50 01 01 00 00 01 00 00 00 0b cd 69 01 05 61  |NP..........i..a|
0010  6c 69 63 65 02 02 00 12                          |lice....|
```

逐字节读：`4e 50` = magic；`01` = version；`01` = cmd；`00` = flags；`00 01` = seq=1；`00 00 00 0b` = body 11 字节；`cd 69` = 校验和；`01 05 61 6c 69 63 65` = TLV(T=1, L=5, "alice")；`02 02 00 12` = TLV(T=2, L=2, 18)。

### 3. 端序：先假设，再用样本证伪

同一个 32 位数 `0x0000000B`（11），大端和小端在字节流里完全不同：

| 端序 | 字节序列 | 常见于 |
|:---:|---|---|
| 大端（网络序） | `00 00 00 0b` | 大多数网络协议、length 字段 |
| 小端 | `0b 00 00 00` | x86 本地结构体直接写出、部分游戏协议 |

判断技巧（从强到弱）：

1. **找已知值**：长度字段附近的 body 实际有多少字节，就能验证哪种读法对得上；
2. **看魔数**：`4e 50` 读成 ASCII 是 `NP`，说明这个协议偏「按字节声明」；
3. **看数值合理性**：`cmd` 一般是个位到几十，若读出来是 16777216，说明端序或字段宽度错了；
4. **看浮点**：`3f 80 00 00` 是大端 1.0，`00 00 80 3f` 是小端 1.0。

### 4. 长度字段的三种口径，必须验证

| 口径 | 含义 | 验证方法 |
|:---:|---|---|
| 只算 body | `total = header_len + body_len` | 常见；用 total 减去已知头长得 body |
| 含头部 | `total = body_len` | 若按 body 解读会多读或少读 header_len |
| 含自身 | 长度字段把自己也算进去 | 少见但存在，差值恰好是字段宽度 |

**别猜。** 拿两条不同长度的消息，列出「长度字段值 − 实际 body 字节数」的差，差恒定就说明口径固定；差随消息变化，说明字段含义不是长度。

### 5. 粘包与半包

TCP 是字节流，**发送方的两次 `send` 和接收方的 `recv` 没有任何对应关系**。发送 A(100 字节)、B(100 字节)、C(100 字节)，接收方可能这样收到：

```text
场景 1（粘包）：recv 返回 250 字节 = A(100) + B(100) + C 的前 50 字节
场景 2（半包）：recv 返回 40 字节  = A 的前 40 字节
场景 3（正常）：recv 返回 100 字节 = 恰好一条 A
```

所以解码器必须是**带缓冲区 + 循环切帧**的形状：

```text
while True:
    把新到的字节追加进 buffer
    while buffer 里至少有一个完整帧:
        按头部读出 body_len
        计算 total = header_len + body_len
        if len(buffer) < total: break      # 半包，等更多数据
        取出 total 字节，解析，从 buffer 删除
```

### 6. 逆向一个未知二进制协议的流程

| 步骤 | 做什么 | 得到什么证据 |
|:---:|---|---|
| 1 | 抓一段同一操作的流量，对比不同请求 | 找出固定前缀 → 魔数 |
| 2 | 找连续 4 字节且值随 body 变化 | 候选 length 字段 |
| 3 | 用两种口径分别切，看哪种能把整段字节刚好切完 | 定界方式 |
| 4 | 对比「同命令、不同参数」的两条消息 | 变化的位置 = 参数字段 |
| 5 | 对比「同参数、不同命令」的两条消息 | 命令字位置 |
| 6 | 找相邻字段的差值是否等于长度 | 变长字段 / TLV |
| 7 | 看末 2/4 字节是否随内容变化 | 校验和 / CRC |
| 8 | 看载荷是否高熵、是否有固定块大小 | 压缩 / 加密 |

**第 3 步是整个逆向的分水岭**：切不对，后面所有字段都会错位。

### 7. Protobuf 的 varint 也值得认识

很多自定义协议借鉴了 Protobuf 的变长整数：每字节最高位表示「后面还有没有」，低 7 位是数据。300 的编码是：

```text
300 = 0b1_0010_1100
低 7 位 0101100 = 0x2C，置继续位 → 0xAC
剩余   0b10     = 0x02，无继续位 → 0x02
编码结果：ac 02（2 字节，而不是 4 字节）
```

看到「每隔一段就出现 `0x80` 以上的字节」的字段，先怀疑 varint，而不是长度字段。

## 动手验证

```powershell
# 在仓库根目录执行
py tools\frame-demo.py
```

本机实测输出（节选开头与解码过程）：

```text
帧 1：24 字节（头 13 + body 11）
  0000  4e 50 01 01 00 00 01 00 00 00 0b cd 69 01 05 61  |NP..........i..a|
  0010  6c 69 63 65 02 02 00 12                          |lice....|
帧 2：23 字节（头 13 + body 10）
  0000  4e 50 01 02 80 00 02 00 00 00 0a c6 a9 03 08 00  |NP..............|
  0010  00 00 78 ff ff ff dd                             |..x....|
```

头部字段表（脚本按偏移打印，和上面的格式表逐项对应）：

```text
  偏移   长度  字段        值
  0     2     magic       4e 50
  2     1     version     01
  3     1     cmd         01
  4     1     flags       00
  5     2     seq         00 01
  7     4     body_len    00 00 00 0b
  11    2     checksum    cd 69
```

然后脚本把两条消息拼成一个 47 字节的流，**每次只喂 3 个字节**，模拟半包：

```text
  块  本次字节   缓冲区剩余   已解出帧
  0   3         3            0
  ...
  6   3         21           0
  7   3         0            1
       → 解出帧 cmd=0x01 seq=1 body_len=11  T=0x01 V=b'alice', T=0x02 V=b'\x00\x12'
  ...
  15  2         0            1
       → 解出帧 cmd=0x02 seq=2 body_len=10  T=0x03 V=b'\x00\x00\x00x\xff\xff\xff\xdd'

[ok] 两帧按 3 字节分块喂入后全部解出，缓冲区清空
[ok] 帧 1 校验和重算一致
[ok] TLV 解析：0x01=alice，0x02=18，0x03=(120, -35)
```

注意第 7 块：缓冲区从 21 变成 0，同时解出 1 帧——**第 24 个字节到齐的瞬间才切帧**，这正是「长度字段定界」在代码里的样子。第三帧的值 `00 00 00 78 ff ff ff dd` 是 `struct.pack("!ii", 120, -35)`，用大端有符号 32 位读回来就是 `(120, -35)`。

## 常见误区

1. **很多人以为 `recv()` 一次就是一条消息，实际它可能返回半条、一条半或三条**，因为 TCP 是字节流，不保留应用层的发送边界。
2. **很多人以为 TCP 会保留发送方 `send()` 的边界，实际不会**，因为 TCP 只保证字节顺序，合并与拆分由内核缓冲区和 MSS 决定。
3. **很多人以为长度字段一定不含头部，实际三种口径都存在**，因为协议设计者可以自由定义，必须用两条样本算出差值来确认。
4. **很多人以为小端大端靠猜，实际可以用长度字段与 body 实际长度互相验证**，因为长度是少数「能被字节数直接检验」的字段。
5. **很多人以为 Wireshark 里一个 TCP 段就是一条业务消息，实际一段里可能有 0.3 条或 2 条**，因为重组与切分和业务边界无关。

## 自测

**1. 头部 13 字节、`body_len = 11`，这条消息在 TCP 流里总共占多少字节？**

- **考点**：长度口径
- **应明白**：`total = header_len + body_len`
- **算会**：`13 + 11 = 24`；并说出「如果长度字段含头部，则 total 就是 11，需要重新验证口径」

**2. 收到字节 `03 61 62 63 02 64 65`，协议规定「1 字节长度 + 该长度的 ASCII」，能解出几条消息？**

- **考点**：长度前缀定界
- **应明白**：先读长度，再按长度取内容，循环
- **算会**：`03` + `abc`，`02` + `de`，共 2 条；剩余 0 字节，没有半包

**3. 某协议头部 12 字节，长度字段值 `0x20`，但按 body_len 切出来 total = 44 字节，实际消息只有 32 字节。最可能的解释是什么？**

- **考点**：长度口径假设错误
- **应明白**：44 = 12 + 32，差正好是头部长度
- **算会**：长度字段的含义是「含头部的总长度」，应改为 `total = len_field` 而不是 `header + len_field`
