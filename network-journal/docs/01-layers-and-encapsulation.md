# 01 · 分层模型与数据封装

> 一句话：一次 HTTP 请求从应用到网线，每一层只在自己的头部加上该层的信息，不多也不少；排障的第一步永远是判断「问题在哪一层」。

## 是什么 / 为什么重要

分层不是为了画图好看，而是为了**分工与替换**：IP 层不关心上面跑的是 TCP 还是 UDP，以太网不关心 IP 包里装的是什么。每层只解决自己的问题，所以换掉 Wi-Fi 不影响 HTTP，换掉 HTTP/1.1 也不影响 TCP。

封装（encapsulation）就是这套分工的物理表现：数据从应用层往下走，每层在前面加一个头；接收端从下往上走，每层剥掉自己的头，把剩下的交给上一层。**排障时你说「这是传输层问题」，依据就是「这一层该负责的事没做到」**：TCP 该重传没重传、该 ACK 没 ACK。

## 机制与结构

### 1. 四层模型与 OSI 的对应关系

| OSI 七层 | TCP/IP 四层 | 这一层处理什么 | 例子 |
|:---:|:---:|---|---|
| 应用层 / 表示层 / 会话层（5–7） | 应用层 | 业务语义、编码、会话 | HTTP、DNS、TLS（介于应用与传输之间） |
| 传输层（4） | 传输层 | 端到端、端口、可靠性 | TCP、UDP、QUIC |
| 网络层（3） | 网络层 | 寻址与路由，跨网段投递 | IPv4、IPv6、ICMP |
| 数据链路层（2）+ 物理层（1） | 网络接口层 | 同一链路内的帧传输 | Ethernet、Wi-Fi、ARP |

**为什么 TCP/IP 只有四层**：OSI 的表示层和会话层在现实协议里几乎没有独立实现（序列化、加密、会话复用都塞进了应用协议），链路层和物理层由网卡与驱动一起处理，所以工程上合成一层。

### 2. 封装顺序：一次 HTTPS 请求

```mermaid
flowchart LR
    A["HTTP 报文<br>请求行 + 头 + 空行"] --> B["TLS record<br>5 字节头 + 密文 + 16 字节 tag"]
    B --> C["TCP 段<br>20 字节头（无选项）"]
    C --> D["IPv4 包<br>20 字节头"]
    D --> E["以太网帧<br>14 字节头 + 数据 + 4 字节 FCS"]
    E --> F["物理层比特"]
```

接收端反方向做**解封装**：网卡校验 FCS → 驱动剥掉以太网头 → 内核看 EtherType 交给 IPv4 → IPv4 校验头、看 protocol 交给 TCP → TCP 按端口交给 socket → 内核把 TLS 记录交给应用 → TLS 解密后得到 HTTP 报文。

### 3. 每层加了多少字节（HTTPS，GET 请求）

以 `GET / HTTP/1.1` 加三个头为例，HTTP 明文共 75 字节：

```text
GET / HTTP/1.1\r\n            16 字节
Host: example.com\r\n         19 字节
User-Agent: curl/8.22.0\r\n   25 字节
Accept: */*\r\n               13 字节
\r\n                           2 字节
                              ---------
                              75 字节
```

| 层 | 加的东西 | 增量 | 累计 |
|:---:|---|---:|---:|
| HTTP | 请求行、头、空行 | — | 75 |
| TLS 1.3 | 5 字节 record 头 + 16 字节 AEAD tag | +21 | 96 |
| TCP | 20 字节头（无选项） | +20 | 116 |
| IPv4 | 20 字节头（无选项） | +20 | 136 |
| Ethernet II | 14 字节头（目的 MAC 6 + 源 MAC 6 + 类型 2） | +14 | 150 |
| FCS | 4 字节帧校验（网卡算，抓包软件常不显示） | +4 | 154 |

走 HTTP（不加密）时没有 TLS 那 21 字节，帧长变成 129 字节。**同样是「一个 GET」，HTTPS 在链路上只多 21 字节，却多了密钥协商和证书校验的往返** —— 这是第 6 篇的主题。

### 4. 一个以太网帧里的嵌套结构

```text
 偏移  0        6        12       14                    14+payload
      +--------+--------+--------+----------------------+-----+
      | Dst MAC| Src MAC| Type   |  Payload             | FCS |
      |  6 B   |  6 B   | 2 B    |  46 – 1500 B         | 4 B |
      +--------+--------+--------+----------------------+-----+
                         0x0800
                            │
        ┌───────────────────┘
        ▼
      +---------+---------+----------+--------+
      | IPv4 头 | TCP 头  | TLS      | HTTP   |
      | 20 B    | 20 B    | 21 B     | 75 B   |
      +---------+---------+----------+--------+
      |<--- IPv4 total_length = 136 字节 --->|
```

两个容易记错的边界：

- **MTU 1500 是 IPv4 包的总长上限**（含 IP 头），不是帧长。加上以太网头和 FCS，帧最大 1518 字节。
- `total_length` 字段只算 IPv4 头加它的载荷，**不算链路层的 18 字节**（14 头 + 4 FCS），也不算前导码。

### 5. 每层的 PDU 名字

| 层 | PDU 叫法 | 起止标志 |
|:---:|---|---|
| 应用层 | 报文（message） | 协议自定义（HTTP 靠 `Content-Length` / chunked） |
| 传输层 | TCP 段（segment）、UDP 数据报（datagram） | TCP 头 / UDP 头 |
| 网络层 | 分组 / 数据包（packet） | IPv4 头 |
| 链路层 | 帧（frame） | 前导码 + SFD 开头，FCS 结尾 |

### 6. 封装与解封装的对偶关系

| 方向 | 动作 | 谁来做 | 失败会怎样 |
|:---:|---|---|---|
| 发送（封装） | 逐层加头 | 应用 → 内核协议栈 → 网卡 | 头字段算错（长度、校验和）→ 对端丢弃 |
| 接收（解封装） | 逐层剥头并分用 | 网卡 → 内核 → 应用 | EtherType 不认识 → 丢弃；端口无监听 → RST |

**解封装的关键是「分用」（demultiplexing）**：以太网用 EtherType 决定交给 IPv4 还是 ARP；IPv4 用 protocol 决定交给 TCP、UDP 还是 ICMP；TCP/UDP 用目的端口决定交给哪个 socket。每一层都有一个「下一步交给谁」的字段——**这五个字段就是排障时的第一组线索**。

## 动手验证

### 验证 1：亲手看 IP 头的字节

```powershell
cd labs\01-packet-craft
py craft.py
```

预期在【4】IPv4 头一节看到：

```text
0000  45 00 00 28 1b 2d 40 00 40 06 9b 63 c0 00 02 0a  |E..(.-@.@..c....|
```

逐字段读：`45` = 版本 4 + 头长 5（20 字节）；`00 28` = 总长 40；`40` = TTL 64；`06` = 协议 TCP；`c0 00 02 0a` = `192.0.2.10`。最后 `9b 63` 是 IP 头校验和，可用脚本里的 `checksum()` 重算验证为 0。

### 验证 2：用 curl 看应用层，确认「上面看不到 IP 头」

```powershell
curl.exe -v --max-time 8 -o NUL http://example.com/
```

本机实测（curl 8.22.0）输出里的关键行：

```text
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.22.0
> Accept: */*
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Transfer-Encoding: chunked
```

`curl -v` 只能显示应用层。想看传输层和网络层，必须抓包（第 8 篇）或自己解析字节（lab）。

### 验证 3：算一遍，别背

- HTTP 明文 75 字节 + TCP 20 + IPv4 20 + Ethernet 14 = **129 字节**（不含 FCS）。
- HTTPS 再加 21 字节 TLS 开销 = **150 字节**（不含 FCS）。
- MTU 1500 时，IPv4 + TCP 无选项的最大载荷 = `1500 - 20 - 20 = 1460` 字节，这就是 **MSS**。

## 常见误区

1. **很多人以为「分层就是每层把数据复制一份再打包」，实际是只加头部、载荷共享同一块内存**，因为复制会带来无谓的带宽与 CPU 开销，内核用 sk_buff / mbuf 这类结构在不同层之间传递指针。
2. **很多人以为 MTU 1500 是整个帧的长度，实际它是 IPv4 包（含 IP 头）的上限**，因为 MTU 的定义在 IP 层；以太网帧最大 1514 字节（不含 FCS），加上 FCS 是 1518。
3. **很多人以为 OSI 七层和 TCP/IP 四层是一一对应的，实际应用层对应 OSI 的 5–7 层、网络接口层对应 1–2 层**，因为 OSI 是教学模型，TCP/IP 是实现模型。
4. **很多人以为 HTTP 一定跑在 TCP 上，实际 HTTP/3 跑在 QUIC（UDP）之上**，因为 TCP 的队头阻塞拖累了多路复用，HTTP/3 干脆换了传输层。
5. **很多人以为 TLS 属于传输层，实际它夹在 TCP 与应用之间**，因为 TLS 需要一条可靠的字节流（所以用 TCP），又必须理解应用协议；跑在 UDP 上的版本叫 DTLS。

## 自测

**1. 一个 75 字节的 HTTP 请求走 HTTPS，以太网帧（不含前导码与 FCS）是多少字节？请写出每一层的加法。**

- **考点**：封装顺序与各层头部长度
- **应明白**：TLS 记录头 5 + tag 16，TCP 20，IPv4 20，以太网 14
- **算会**：`75 + 21 + 20 + 20 + 14 = 150`，并能说出这 21 字节在 HTTP/3 里为什么不存在（QUIC 自己加密，没有 TLS record 层）

**2. MTU 1500、IPv4 无选项、TCP 带 12 字节选项（时间戳），MSS 是多少？**

- **考点**：MSS 的定义与计算
- **应明白**：MSS = MTU − IP 头 − TCP 头
- **算会**：`1500 - 20 - 32 = 1448`，而不是背 1460

**3. 抓包看到 `Ethernet II, Type: IPv4 (0x0800)`，下一层一定是 IPv4 吗？如果是 `0x0806` 呢？**

- **考点**：EtherType 的分用
- **应明白**：类型字段决定载荷交给谁
- **算会**：`0x0800` → IPv4；`0x0806` → ARP，而 ARP 帧里**没有 IP 头**，不能用「以太网 → IP」的固定顺序去套
