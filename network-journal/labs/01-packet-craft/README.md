# Lab 01 · 手工构造 IPv4 / TCP / UDP / DNS 报文字节

对应笔记：[docs/01 · 分层与封装](../../docs/01-layers-and-encapsulation.md)、[docs/02 · 以太网/ARP/IPv4](../../docs/02-ethernet-arp-ip.md)、[docs/03 · TCP 三次握手](../../docs/03-tcp-handshake.md)、[docs/05 · UDP 与 DNS](../../docs/05-udp-and-dns.md)

## 目的

1. 不依赖任何抓包库，用 `struct` / `ipaddress` / `socket` 把报文的**每一个字节**亲手拼出来；
2. 亲手算对 IPv4 头校验和、TCP/UDP 伪首部校验和；
3. 写解析函数把字节读回成字段字典，体会「构造」与「解析」互为逆运算；
4. 把 DNS 的 QNAME 编码/解码往返跑通，为后面看 Wireshark 里的十六进制打底。

**本脚本不发送任何数据包**：只用 RFC 5737 的文档专用地址（`192.0.2.0/24`）在内存里构造字节，运行不产生任何网络流量。

## 原理

四件必须自己算一遍的事：

1. **IPv4 头校验和**：把校验和字段当 0，16 位一组反码求和、进位回卷，最后取反回填。验证时把带校验和的整个头再算一遍，结果必须是 0。
2. **TCP/UDP 伪首部**：源 IP + 目的 IP + 保留 0 + 协议号 + 传输层长度，只参与校验和计算，**不真的出现在报文里**。
3. **DNS QNAME**：每段前面 1 字节长度，最后补 0；完整解析器还要处理压缩指针（本 lab 遇到指针会显式报错，不装作能解析）。
4. **端序**：网络字节序是大端，Python 用 `struct` 的 `!` 前缀；`struct.pack("!H", 53)` 得到 `00 35`。

一句话：**构造和解析是同一张字段表的两个方向**，能写出来、也能读回来，才算真的认识这些字节。

## 读这个输出，要看什么

| 现象 | 为什么 |
|:---:|---|
| `03 77 77 77 07 65 78 61 6d 70 6c 65 03 63 6f 6d 00` | QNAME 的「长度 + 标签」编码，最后补 0 |
| `cf 08` = 53000 | 端口是大端（网络序） |
| `00 29` = 41 | UDP length 必须等于 8 + 33 |
| `50` 在 TCP 偏移 12 | 高 4 位是 data offset = 5，即 20 字节头 |
| `02` 在 TCP 偏移 13 | 只有 SYN 置位 |
| `45` 在 IPv4 偏移 0 | 版本 4 + 头长 5 |
| `9b 63` = IP 校验和 | 把校验和一起参与重算，结果应为 0 |
| `0a e1` = TCP 校验和 | 必须把**伪首部**（源/目的 IP、协议号、长度）一起算进去 |

## 自测题

> 每道题写清三件事：**考点** · **做完你应该明白什么** · **怎么算真的会了**。
> 先只看题干自己想，答完再对照。

### 自测 1：把 `TCP_FLAG_SYN` 改成 `TCP_FLAG_SYN | 0x10`（SYN+ACK），输出的校验和会变吗？为什么？

**考点**：校验和的覆盖范围

**做完你应该明白**
- 校验和覆盖 TCP 头 + 载荷 + 伪首部，改任何一个字节都会变
- TCP 校验和字段本身在计算时算 0，算完再回填
- 改 flags 不影响长度，但影响结果

**怎么算真的会了**
你能先预测「会变」，再改代码验证，并解释「为什么重算后仍然等于 0」。

**常见错误**
- 以为校验和只校验载荷 —— 头部也在内
- 忘记伪首部，算出来的值对不上任何抓包

---

### 自测 2：把 DNS 查询的域名换成 `a.example.org`，QNAME 编码后是多少字节？

**考点**：QNAME 编码规则

**做完你应该明白**
- 每个标签 = 1 字节长度 + 标签内容
- 末尾必须有 1 个 0 字节
- 总长 = 各标签长度和 + 标签数 + 1

**怎么算真的会了**
`01 61 07 65 78 61 6d 70 6c 65 03 6f 72 67 00`，共 15 字节；跑一遍 `py craft.py` 看解析回来了没有。

**常见错误**
- 算成 14（忘了结尾的 0）
- 把点号也编码进去（DNS 的 QNAME 里没有点，点是显示时才加的）

---

### 自测 3：为什么 UDP 的 `length` 字段是 41，而 IPv4 的 `total_length` 是 40？

**考点**：两个长度字段的口径

**做完你应该明白**
- UDP length 覆盖「UDP 头 + UDP 载荷」= 8 + 33 = 41
- IPv4 total_length 覆盖「IP 头 + IP 载荷」= 20 + 20 = 40（这里装的是 TCP）
- 二者统计的是**不同报文**，不能直接比较

**怎么算真的会了**
你能指出「UDP 那 41 字节如果装进 IP，IPv4 total_length 会是 20 + 41 = 61」，并知道这正是 `tools/make-pcap.py` 里 DNS 帧的 `total_length`。

**常见错误**
- 以为 UDP length 包含 IP 头
- 以为两个字段应该相等

---

### 自测 4：把 `SRC_IP` 改成 `10.0.0.1`，哪些字段会变？

**考点**：校验和依赖的输入

**做完你应该明白**
- IPv4 头校验和会变（源 IP 在头里）
- TCP 校验和会变（伪首部含源 IP）
- UDP 校验和会变（同理）
- 长度字段不变

**怎么算真的会了**
你能列全「IPv4 checksum、TCP checksum、UDP checksum」三处，并说明「伪首部不是报文的一部分，但参与计算」。

**常见错误**
- 只改 IPv4 校验和，忘了 TCP/UDP

## 进阶

- 加一个 **IPv4 选项**（如记录路由），让 IHL 变成 6，观察 `data_offset`/长度字段怎么变；
- 构造一个**分片**：把 4000 字节载荷按 MTU 1500 切三片，打印每片的 ID / MF / offset；
- 把 TCP 段换成 **SYN+ACK**，用 [docs/03](../../docs/03-tcp-handshake.md) 的规则检查 `seq`/`ack` 是否符合预期；
- 用 [tools/make-pcap.py](../../tools/make-pcap.py) 把构造的字节写成 pcap，装好 Wireshark 后打开对照。
