# 实验 01 · 结构体布局与偏移

> 这节课**只解决一个问题**：`0x10` 这个数字是怎么来的。  
> 不是"大概知道偏移是什么"，是能手算出它、能用程序验证它、能解释它为什么是这个值。

---

## 0. 先建立一个画面

不要一上来就想"游戏"。先想这个：

```
内存 = 一条很长很长的纸条，上面每 1 毫米有一个格子，格子从 0 开始编号
```

一个变量，就是纸条上**连续的若干格**。  
一个结构体，就是**一整段连续的格子**，里面按顺序塞了几个字段。

`Entity` 占 40 格（0x28 字节）。它的第一个格子有一个地址，叫**首地址（base）**。

那么：

```
hp 的地址 = base + 16      ← 前面塞了 id(4 格) + pos(12 格) = 16 格
```

**16 用十六进制写就是 0x10。这就是全部的秘密。**

为什么游戏分析里到处是 `+0x10`、`+0x1A4` 这种东西？因为那些程序里的"血量"字段，离结构体开头就是那么远。

### 1.4 编译只做一次

改 `.c` / `.h` 之后才需要重新 `build.bat`。只是看输出的话，直接 `offsets.exe`。

编译参数每个都有用，别省略：

| 参数        | 作用     | 去掉会怎样              |
| --------- | ------ | ------------------ |
| `-O0`     | 关优化    | 优化会把没被读的字段删掉，布局就变了 |
| `-g`      | 生成调试信息 | 调试器里看不到变量名和行号      |
| `-no-pie` | 固定加载地址 | 每次运行地址都变，教学阶段会把你逼疯 |

本机实测输出（`offsets.exe`）：

```
sizeof(Entity) = 0x28  (40 bytes)

  id      offset 0x00   size  4
  pos     offset 0x04   size 12
  hp      offset 0x10   size  4
  team    offset 0x14   size  1
  _pad    offset 0x15   size  3
  name    offset 0x18   size 16

一个实例的首地址        00000000005FFEA0
  &e.id    00000000005FFEA0   = base + 0x00
  &e.hp    00000000005FFEB0   = base + 0x10   <- 记住这一行
  &e.name  00000000005FFEB8   = base + 0x18
```

**自己核对一遍加法**：`0x00 + 4 = 0x04`，`0x04 + 12 = 0x10`，`0x10 + 4 = 0x14`，`0x14 + 1 = 0x15`，`0x15 + 3 = 0x18`，`0x18 + 16 = 0x28`。  
一路加下来刚好等于 `sizeof`，说明你算对了。

## 2. 三个必须记住的事实

**事实一：地址 = 首地址 + 偏移。** 没有魔法，没有查表，就是加法。

**事实二：偏移由"字段顺序 + 字段大小"决定。** 所以换个顺序，偏移全变。

**事实三：编译器会在中间偷偷插空格（填充 / padding）。** 这就是 `_pad[3]` 存在的理由：  
`hp` 是个 4 字节的 float，它必须落在能被 4 整除的地址上（0x10 ✓）。`team` 只占 1 字节，占掉 0x14。  
下一个 `name` 是无所谓对齐的 char 数组，本来 0x15 就能放，但**整个结构体的大小要是最大成员的整数倍**（这里有 4 字节成员），所以编译器塞了 3 个没人用的字节，把 `name` 推到 0x18。

> 这就是你以后分析别人程序时，为什么总在字段之间看到"来历不明的 4 个字节"。

## 3. 动手三件事（别只是看，做了才算学会）

先**猜**再跑，猜错的地方才是你真正学到的地方。

**实验 A · 换顺序**  
把 `entity.h` 里 `hp` 和 `id` 两行对调。  
先纸上算：`hp` 现在应该在哪？`name` 呢？`sizeof` 变了没？  
然后再 `build.bat && offsets.exe` 验证。**猜错就写下来为什么错。**

> **实测记录（2026-11-25）**：对调 `hp` 与 `id` 之后实跑结果——
>
> ```
>   id      offset 0x10   size  4     <- 原来 0x00
>   pos     offset 0x04   size 12     <- 未变
>   hp      offset 0x00   size  4     <- 原来 0x10
>   team    offset 0x14   size  1     <- 未变
>   _pad    offset 0x15   size  3     <- 未变
>   name    offset 0x18   size 16     <- 未变
>   sizeof(Entity) = 0x28             <- 未变
> ```
>
> 三条结论：
>
> 1. 两个**等大**字段互换，只互换偏移，后面的字段完全不受影响——因为边界位置没动。
> 2. `sizeof` 不变，理由同上：总字节数没变。
> 3. **注释没跟着改就是错的**：改完 `entity.h` 里 `hp` 那行还写着 `+0x10`，  
>    而程序打印的是 `0x00`。注释是人的承诺，编译产物才是事实。

**实验 B · 删掉填充**  
把 `uint8_t _pad[3];` 整行删掉。  
预测 `name` 的偏移。跑一遍。如果和你猜的不一样，回到事实三再读一遍。

**实验 C · 换个类型**

这一个改动会连带影响后面所有字段的偏移和 `sizeof`。

## 5. 常见坑

- **`sizeof(Entity*)` 不等于 `sizeof(Entity)`**：指针只有 8 字节。
- **32 位和 64 位布局不同**：指针大小变了，填充也跟着变。本课一律 64 位。
- **别用 `-O2` 做这类实验**：字段会被优化掉，你会怀疑人生。
- **`0x10` 是十六进制**，等于十进制 16。第一次接触容易数错。
- **`.bat` 文件里不要写中文**。cmd.exe 按系统 OEM 码页（简体中文是 GBK）读取批处理，  
  而编辑器默认存成 UTF-8，中文会变成乱码字节，\*\*连注释都会被执行\*\*——  
  实测过：`echo` 被截成 `cho`，`REM` 后面的乱码直接报"不是内部或外部命令"。  
  本目录的 `.bat` 全部是纯 ASCII，是故意的。
- **控制台里中文变乱码？** 源码是 UTF-8，cmd 默认按 GBK（代码页 936）解释字节。  
  数字和英文在两个码页里是同一批字节，所以不受影响；中文字节会被错读成"涓枃"这类鬼东西。  
  两种解法：① 程序输出只用 ASCII（本目录采用，最稳）；② 先 `chcp 65001` 再运行。  
  `run.bat` 里两样都做了。
