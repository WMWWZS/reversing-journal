# 实验 05 · AOB 特征扫描：游戏更新之后，偏移废了怎么办

> 实验 04 你拿到一条链，起点是 `base + 0x7030`。
> 这一节的靶子是同一个程序的 **v2**：多了几个全局变量，`g_world` 的槽位往外挪了 0x20。
>
> **写死的偏移当场失效。** 这不是意外，是每次游戏更新都会发生的事。

---

## 0. 前置知识

| 需要会 | 来自 | 用在哪一步 |
|---|---|---|
| 走指针链、验证终点 | [../04-pointer-chain](../04-pointer-chain) | 扫到候选后要用链验证 |
| 知道偏移会因为重排而失效 | [../01-struct-layout](../01-struct-layout) | 理解为什么旧偏移读成 0 |
| 读指令字节（objdump 看一眼） | 本节会讲 | 认出 `48 8B 05` 是什么 |

**不需要**：改代码（09）、反汇编器用得很熟。

## 0.5 游戏里这对应什么

| 游戏里 | 进程里 | 具体到字节 |
|---|---|---|
| 游戏更新，界面没变 | `.data` 里变量重排 | 旧的 `base+0x7030` 读到 0 |
| 「访问世界指针」这件事 | `mov rax,[rip+disp32]` | `48 8B 05 ?? ?? ?? ??` |
| 指令里的相对偏移 | disp32 跟着变量一起变 | `目标 = 指令 + 7 + disp` |
| 满屏都是同形状指令 | 候选很多 | 必须用链验证，只留一条 |

类比：**门牌号变了，但"从这条路拐进去第三个红绿灯"这个描述没变。**

## 1. 先看它怎么失效的（实测）

```
=== 第 1 步：旧配置还有效吗 ===
  base + 0x7030 的 8 个字节 = 0x0
  沿它走不通 -> 旧偏移已失效，正是这一节要解决的问题
```

`0x7030` 在新版里是别的变量（这里是 0），顺着它走链立刻断。**偏移是编译产物，不是契约。**

---

## 2. 换个思路：不找变量，找"访问变量的指令"

不管 `g_world` 挪到哪，代码总得访问它。x64 下访问全局变量长这样：

```asm
mov  rax, [rip + disp32]        ; 48 8B 05 ?? ?? ?? ??
```

- `48 8B 05` 是**指令形状**（opcode + modrm），几乎不会变；
- `disp32` 是"从下一条指令往回/往前数多少字节"，**它跟着变量地址一起变**。

所以真正稳定的信息不是 disp，而是**关系**：

```
槽位地址 = 指令地址 + 7 + disp32
```

7 是指令长度（`48 8B 05` 3 字节 + disp32 4 字节）。扫描时把 disp 当通配符（`??`），
命中之后再把它解出来，就能**重新算出**槽位地址。

## 3. 实测输出（本机）

```
=== 第 2 步：扫描 48 8B 05 ?? ?? ?? ?? ===
  命中 #1  指令 @ base+0x01014 : 48 8B 05 F5 34 00 00
          算出目标 = 0x140004510  (模块内偏移 0x4510)
  ...
  命中 #12 指令 @ base+0x013F4 : 48 8B 05 05 31 00 00
          算出目标 = 0x140004500  (模块内偏移 0x4500)

[+] 找到了：
    指令地址   = base + 0x166B
    指令字节   = 48 8B 05 DE 59 00 00
    相对偏移   = 23006 (0x59DE)
    槽位地址   = 指令 + 7 + 相对偏移 = 0x140007050
    槽位偏移   = base + 0x7050   <- 这是新的静态偏移
    沿链读 World = 0xDF470

共扫到 15 条候选指令，其中 1 条能走通链。
```

注意最后两行：**15 条候选里只有 1 条通过验证**。扫描会带来噪声，所以必须有验证环节——
这里用的是"顺着它算出的槽位走链，能不能读到 `bot-1`"。没有验证的扫描，等于在猜。

## 4. 这条技术在工作里长什么样

```
CE / x64dbg: 右键目标地址 -> "找出是什么访问了这个地址"
             得到一条指令，比如  mov rax,[rip+0x59DE]
抄下来：     48 8B 05 DE 59 00 00
做成特征：   48 8B 05 ?? ?? ?? ??        （disp 变通配）
程序里：     模块内扫描 -> 解 disp -> 算目标 -> 验证 -> 得到新偏移
```

这就是"特征码"（signature / AOB pattern）的全部。它比偏移长寿得多：
游戏更新改了布局，`??` 那 4 个字节跟着变，命中的位置和算法不用动。

## 5. 自己动手

**实验 A · 再更新一次**
在 `target.c` 的全局区再插两个变量，重新编译，跑 `aob.exe`：
预期是"旧偏移又失效"+"扫描仍然找到新偏移"。做两遍，你会对这件事彻底脱敏。

**实验 B · 把通配符写窄一点**
现在只匹配了 3 个字节 `48 8B 05`，所以有 15 条候选。
真实项目里会把后面的字节也带上（比如再跟一条 `48 85 C0` 判断指针非空），
候选数立刻掉到 1~2 条。改 `aob.c` 里的匹配条件试试，看候选数怎么变。

**实验 C · 换验证条件**
现在的验证靠 `"bot-1"` 这个名字。把它改成"读到的 hp 在 0~100 之间"，再跑一次。
思考：哪种验证更稳？如果游戏里名字被加密了呢？

## 6. 判定标准

> 给一个**没有源码、偏移未知**的进程，能用"扫描指令形状 + 解 disp + 验证链"三步
> 重新定位到那个全局指针，并说清楚每一步为什么不会因为更新而失效。

---

## 7. 常见坑

- **忘了 `+7`**：`48 8B 05` 后面的 disp 是相对**下一条指令**的，不是相对当前指令。
  少加 3 个字节，算出来的地址整体偏 3，永远对不上。
- **只扫代码段**：`VirtualQueryEx` 里区分 `PAGE_EXECUTE_READ` 会更快，但漏扫也没关系，
  多扫几 MB 而已。真正的问题是**没验证**。
- **把 `disp32` 当无符号**：它是有符号 32 位，可能是负数（变量在指令前面）。
- **以为特征一定唯一**：先看候选数，再决定要不要补字节。唯一性是**验证**出来的，不是假设的。
- **忘了 ASLR**：真实程序里模块基址每次都变，而特征扫描本来就基于"模块内偏移"，
  天然免疫这一点——这也是它比绝对地址好用的原因。
