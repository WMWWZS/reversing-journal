# 实验 02 · 没有源码，把偏移挖出来

> 这一节把 `game.c` 的源码**收起来**。
> 你手上只有一个跑着的进程、一堆十六进制，和一句"血量在掉"。
> 目标：把 `hp` 的偏移找出来，并且**用五条互相印证的证据**证明你对。

---

## 0. 上一节和这一节的差别

| | 实验 01 | 实验 02 |
|---|---|---|

真实目标永远没有第二种待遇——你拿到的永远是 exe。

## 1. 怎么跑

双击 `run.bat`。它会做三件事：

1. 编译 `probe.exe`
2. 另开一个窗口把 `game.exe` 跑起来（那个窗口别关）
3. 在**当前**窗口里对 `game.exe` 做只读探测

也可以手动分两个窗口跑：

```bat
REM 窗口 A
cd ..\01-struct-layout
game.exe

REM 窗口 B
cd labs\02-find-offset
probe.exe 92.5
```

> `92.5` 是 `game.exe` 屏幕上打印的 `[0].hp` 最终值。**先看游戏输出，再抄数字**——
> 抄错了就搜索不到，这不是 bug，是你的输入错了。

---

## 2. 原理：一个 float 在内存里长什么样

`92.5` 这个数在内存里不是字符串 `"92.5"`，是 4 个字节：

```
92.5  ->  IEEE754 单精度  ->  0x42B90000  ->  内存里倒着放：00 00 B9 42
```

AMD64 是**小端序（little-endian）**：低位字节排在低地址。
所以你在十六进制 dump 里看到的顺序，和你在计算器里算出来的顺序是颠倒的。

`probe.exe` 干的就是这件事：把这 4 个字节拿去整个模块里搜。

## 4. 五条证据链（照这个顺序读）

**证据 1 · 命中点**
`0x07050` 处是 `00 00 B9 42`，正好是 92.5。这是我们搜索的目标，找到了。

**证据 2 · 往回找结构体开头**
往上一行 `0x07040` 是 `01 00 00 00` —— 整数 1。
`game.c` 里第一个实体的 `id` 就是 1。这是**结构体的开头**。

**证据 3 · 算偏移**
`0x7050 - 0x7040 = 0x10`。
所以 **`hp` 的偏移 = 0x10**。和实验 01 的 `offsetof` 结果一模一样。

**证据 4 · 验证布局（不是只验一个点）**
- `0x07058` 起是 `62 6F 74 2D 31` → ASCII `"bot-1"`，这就是 `name`，说明 `name` 在 `+0x18`。
- `0x07054`～`0x07057` 是四个 `00`：`team`（1 字节）+ 3 字节**填充**。上一节那个 `_pad[3]` 在这里现形了。
- `0x07068` 又出现 `02 00 00 00` → 第二个实体，`id = 2`。
- 步长 `0x7068 - 0x7040 = 0x28` → 正好等于 `sizeof(Entity)`。

**证据 5 · 值对得上**
`0x07078` 处 `00 00 A5 42` = 0x42A50000 = **82.5**，正是 `[1].hp`。
说明这一整片就是那个实体数组，不是巧合撞上的野数据。

---

## 5. 结论表

| 问题 | 答案 | 靠哪条证据 |
|---|---|---|
| 实体数组在哪 | `base + 0x7040` | 证据 2 |
| `hp` 偏移 | `+0x10` | 证据 3 |
| `name` 偏移 | `+0x18` | 证据 4 |
| 一个实体多大 | `0x28` | 证据 4 |
| 填充在哪 | `+0x15`，3 字节 | 证据 4 |

> **一个数字叫猜测，五条互相印证才叫证据。**
> 这是整门课最重要的一句话，没有之一。

## 7. 下一节

你已经有"读"的能力了。下一节 `labs/03-write-memory` 换成**读写**：

`OpenProcess` 加上 `PROCESS_VM_WRITE | PROCESS_VM_OPERATION`，用 `WriteProcessMemory`
把血量写成一个新值，然后观察它被目标进程下一帧算回去——你会第一次意识到
"内存是活的"，也是第一次明白为什么这类工具必须循环写。

那里还用上了这一节的结论：`hp = base + 0x10` 是从结构体布局推出来的，
换成特征扫描时它变成 `name − 0x08`。**同一份知识，两种用法。**
