# 12 · x64dbg 上手：让程序跑起来看

> Ghidra 是「看图纸」，x64dbg 是「上手拆」。
> 静态分析猜出来的东西，要用动态调试验证。

## 它是什么，不是什么

| | Ghidra | x64dbg |
|---|---|---|
| 类型 | 静态分析 | **动态调试** |
| 对象 | 磁盘上的文件 | **正在运行的进程** |
| 强项 | 反编译、交叉引用、结构还原 | 断点、单步、看寄存器/内存 |
| 不能做 | 看运行时的值 | 给出伪代码 |

**两个一起用**，不是二选一：

```
Ghidra 找到可疑函数 → x64dbg 下断点看实际值 → 回 Ghidra 确认
```

## 启动

桌面 `x64dbg` 图标，或：

```
D:\tools\x64dbg\release\x64\x64dbg.exe
```

> 分析 64 位程序用 `x64dbg.exe`，32 位程序用同目录的 `x32dbg.exe`。

## 首屏认识

| 区域 | 内容 |
|---|---|
| 左上 | **反汇编**（当前执行位置的汇编） |
| 右上 | **寄存器**（RAX/RCX/RDX/RSP/RBP/RIP/EFLAGS…） |
| 左下 | **内存 Dump**（按地址看字节） |
| 右下 | **栈**（Stack） |
| 底部 | 命令栏（可以直接敲 `? rcx` 求值） |

## 常用快捷键

| 键 | 作用 |
|---|---|
| `F2` | 下/取消断点 |
| `F9` | 运行（Run） |
| `F7` | 单步**进入**（Step Into） |
| `F8` | 单步**跳过**（Step Over） |
| `Ctrl+F9` | 运行到返回 |
| `Ctrl+G` | 跳转到地址/表达式 |
| `Ctrl+F` | 在当前模块搜索 |
| `Space` | 暂停 |

## 实战：看 `hp` 从 100 变成 70

### 1. 打开程序

`File` → `Open` → 选

```text
E:\harness\reversing-journal\labs\01-struct-layout\player_O0.exe
```

它会停在系统断点（入口处）。

### 2. 找到 `take_damage`

左侧 `Symbols` 标签 → 展开 `player_O0.exe` → 找 `take_damage`（因为编译时带了 `-g`，符号在）。

双击跳过去。

### 3. 下断点

在 `take_damage` 的第一条指令上按 **`F2`**，变红即成功。

### 4. 运行

按 **`F9`**。程序会停在断点处。

### 5. 看参数

此时看右上角寄存器：

| 寄存器 | 应该是 |
|---|---|
| `RCX` | `p` 的地址（一个 0x 开头的数） |
| `RDX` | `30`（伤害值，十六进制 0x1E） |

### 6. 看内存

左下 `Dump` 窗口 → 按 `Ctrl+G` → 输入 `rcx` → 回车。

你会看到 `player` 结构体的原始字节。开头 4 字节应该是 **`64 00 00 00`**，即十进制的 **100**。

### 7. 单步观察

按几次 **`F8`**（单步跳过），每一步后回 `Dump` 窗口刷新（`Ctrl+G` 重新输入 `rcx`）。

你会看到开头 4 字节从 `64 00 00 00`（100）变成 **`46 00 00 00`**（70）。

**这就是"内存里的值真的变了"的直观证据。** 静态分析只能告诉你"这里会减"，动态调试能告诉你"减完是 70"。

## 寄存器面板怎么读

| 寄存器 | 你现在该关注什么 |
|---|---|
| `RIP` | 下一条要执行的指令地址 |
| `RCX` | 第 1 个参数（`p` 指针） |
| `RDX` | 第 2 个参数（`dmg`） |
| `RAX` | 临时值 / 返回值 |
| `RSP` / `RBP` | 栈顶 / 栈帧基址 |
| `EFLAGS` | 标志位（`ZF` `SF` `CF` `OF` 会高亮） |

> `EFLAGS` 里的 `Z` `S` `C` `O` 就是你上一篇学的 ZF/SF/CF/OF。**在这里能亲眼看到它们变化。**

## 和 Ghidra 配合的标准流程

1. **Ghidra**：打开 exe，找到 `take_damage`，看懂它在做什么
2. **x64dbg**：打开同一个 exe，下断点，跑起来
3. 对比：Ghidra 说"减 30"，x64dbg 看到 100 → 70，**假设被证实**
4. 回到 Ghidra 改名、写注释，固化理解

## 常见问题

**Q：打开 exe 后一片 `int3`？**
A：程序还没运行到用户代码。按 `F9` 让它跑，或者先下断点。

**Q：符号列表里没有函数名？**
A：`-g` 编译的才有。strip 过的程序只能用地址和字符串找。

**Q：提示缺少 DLL / 打不开？**
A：确认是 64 位程序配 `x64dbg.exe`，32 位配 `x32dbg.exe`。

**Q：它会改我的文件吗？**
A：不会。x64dbg 只操作运行中的进程内存，磁盘文件不变。

## 自测

**1. 断在 `take_damage` 入口时，`RDX` 的值是多少？为什么？**

- 考点：参数寄存器
- 应明白：第 2 个参数是 `dmg`，调用时传的是 30，所以 `RDX = 0x1E`
- 算会：你能从 `main` 的反汇编里找到"传 30"那一步

**2. 单步走到 `sub eax, [rbp+dmg]` 之后，`EFLAGS` 的哪个位可能变化？**

- 考点：标志位由运算设置
- 应明白：减法会设置 ZF/SF/CF/OF
- 算会：你能说出"如果结果是 70，SF=0、ZF=0"

**3. 为什么 x64dbg 看不到 Ghidra 里的 `in_RCX` 这种名字？**

- 考点：两种工具的视角不同
- 应明白：x64dbg 显示的是**寄存器原值**，`in_RCX` 是 Ghidra 反编译器编的变量名
- 算会：你能解释"同一个东西，两种展示方式"
