# 06 · 网络协议分析

> 客户端可以被完全控制，只有网络这一层是攻击者无法伪造的边界。
> 这也是防护设计的真正战场。

## 为什么先学协议

- 明白哪些数据是「服务端说了算」，才知道客户端加密有没有意义
- 理解封包结构，才能做服务端校验和异常检测
- 大多数外挂最终想达到的目的（改数值、瞬移、透视）都要过网络这一关

## 分析流程

```
抓包 → 找特征 → 定位序列化函数 → 还原结构 → 验证
```

### 1. 抓包

| 目标 | 工具 |
|---|---|
| TCP / UDP | Wireshark |
| HTTPS | mitmproxy（需要处理证书固定） |
| 私有协议 | Wireshark 自定 Decode As，或自己写解析脚本 |
| 加密流量 | 先定位客户端加密函数（动态调试） |

### 2. 协议识别

常见几类：

- **纯文本**：JSON、XML、自定义分隔符
- **Protobuf / FlatBuffers**：有固定前缀或魔数，可用 `protoc --decode_raw` 尝试
- **自定义二进制**：长度 + opcode + payload
- **加密 + 压缩**：先解密后解压

**快速判断技巧**：看前几个字节。长度字段通常在最前面（2 或 4 字节），后面紧跟 opcode。

### 3. 定位序列化代码

两个方向：

- **从网络 API 入手**：`send` / `recv` / `WSASend` / `WSARecv`，下断点看调用栈
- **从字符串入手**：搜字段名、错误信息、协议版本号

UE 的 `UNetConnection`、`FBitReader`、`FArchive` 是常见的分析目标。

### 4. 还原结构

把封包字段和内存里的结构体对上：

```
[2 bytes length][2 bytes opcode][payload...]
                                   ├── entity_id   (4 bytes)
                                   ├── position    (3 × float)
                                   └── flags       (1 byte)
```

用注解工具（如 Wireshark 的 Lua 解析器）写成可复用的解析脚本。

## 加密与校验

| 手段 | 说明 | 应对 |
|---|---|---|
| 对称加密 | AES / ChaCha20 | 找密钥：通常在客户端常量、或从握手推导 |
| 流加密 | RC4 / 自定义 XOR | 常配合密钥轮换 |
| 包签（HMAC/CRC） | 防篡改 | 找签名函数，观察覆盖范围 |
| 序列号 / nonce | 防重放 | 找计数器 |
| 时间戳校验 | 防延迟篡改 | 观察容差窗口 |

> **重点认知**：如果密钥在客户端，它一定能被找出来。加密的作用是**提高成本**，不是保密。

## 客户端预测与服务端校正

现代网络游戏常用这套模型：

1. 客户端本地预测移动 → 立刻反馈，手感好
2. 服务端权威计算 → 定期下发校正
3. 客户端平滑对齐

**这给了作弊者操作空间**：预测阶段的客户端状态可以被篡改。所以防护的重点是：

- 服务端必须独立校验移动的物理合理性（速度、加速度、碰撞）
- 校正必须覆盖所有关键状态，不能只校正部分字段
- 对「持续偏离但又没超出单帧阈值」的慢速作弊，需要统计检测

## 防护视角：服务端校验清单

| 校验项 | 检查什么 |
|---|---|
| 移动 | 速度上限、加速度、碰撞、地图边界、传送频率 |
| 战斗 | 命中判定、射速、视线遮挡、伤害范围 |
| 经济 | 所有交易的收支平衡、物品来源 |
| 时间 | 操作间隔、CD、会话时长 |
| 顺序 | 状态机合法性（不能跳过前置条件） |
| 统计 | 长期行为偏离、异常胜率、举报聚合 |

> **原则：客户端发来的每一个字节都当作恶意输入处理。**
