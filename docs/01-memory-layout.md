# 01 · 内存布局：逆向的第一性原理

> 逆向工程的全部工作，本质上就是还原两样东西：
> **① 数据是怎么排布的（偏移）　② 代码是怎么操作这些数据的（指令）**

## 实验答案：Player 结构体在内存里的样子

```c
typedef struct {
    int   hp;
    int   max_hp;
    float x, y, z;
    char  name[16];
    int   flags;
} Player;
```

编译器报告的实际布局：

```
sizeof(Player) = 40  (0x28)
hp      offset =  0  (0x00)
max_hp  offset =  4  (0x04)
x       offset =  8  (0x08)
y       offset = 12  (0x0c)
z       offset = 16  (0x10)
name    offset = 20  (0x14)
flags   offset = 36  (0x24)
```

### 对齐规则

- 每个字段的起始偏移必须是其自身大小的整数倍
- 结构体总大小要补齐到最大对齐成员的整数倍

逐个算一遍：

| 字段 | 大小 | 起始偏移 | 占用区间 |
|---|---:|---:|---|
| `hp` | 4 | 0 | 0 – 3 |
| `max_hp` | 4 | 4 | 4 – 7 |
| `x` | 4 | 8 | 8 – 11 |
| `y` | 4 | 12 | 12 – 15 |
| `z` | 4 | 16 | 16 – 19 |
| `name[16]` | 16 | 20 | 20 – 35 |
| `flags` | 4 | 36 | 36 – 39 |

`flags` 是 int，要求 4 字节对齐，而 20+16=36 正好是 4 的倍数，所以直接落在 36。总大小 40 也是 4 的倍数，尾部无需补齐。

> **反例**：如果把 `name` 改成 `char name[13]`，它占 20–32，下一个可用偏移是 33。33 不是 4 的倍数，编译器会补 3 个字节，让 `flags` 从 **36** 开始（而不是 33）。这 3 个字节就是**填充（padding）**。
>
> 逆向时看到两个字段之间有「空档」，多半就是填充。这也是为什么**不能靠 sizeof 猜布局**，必须看实际偏移。

## -O0 反汇编：教科书式

```asm
0000000140001450 <take_damage>:
  140001450:  push   rbp
  140001451:  mov    rbp,rsp
  140001454:  mov    [rbp+0x10],rcx     ; 第1个参数 p
  140001458:  mov    [rbp+0x18],edx     ; 第2个参数 dmg

  14000145b:  mov    rax,[rbp+0x10]     ; rax = p
  14000145f:  mov    eax,[rax]          ; eax = p->hp     ← 偏移 0
  140001461:  sub    eax,[rbp+0x18]     ; eax -= dmg
  140001464:  mov    rdx,[rbp+0x10]
  140001468:  mov    [rdx],eax          ; p->hp = 结果   ← 偏移 0

  14000146a:  mov    rax,[rbp+0x10]
  14000146e:  mov    eax,[rax]
  140001470:  test   eax,eax
  140001472:  jns    14000147e          ; hp >= 0 则跳过
  140001474:  mov    rax,[rbp+0x10]
  140001478:  mov    [rax],0x0          ; p->hp = 0
  14000147e:  nop
  14000147f:  pop    rbp
  140001480:  ret
```

对应 5 行 C 代码。关键观察：

- `[rax]` 是偏移 0 → `hp`
- `[rax+0x4]` 是偏移 4 → `max_hp`（在 `heal` 函数里出现）
- `jns` = jump if not sign，即 `hp >= 0` 时跳转

## -O2 反汇编：信息被压缩

```asm
0000000140001450 <take_damage>:
  140001450:  sub    [rcx],edx          ; p->hp -= dmg
  140001452:  xor    edx,edx
  140001454:  mov    eax,[rcx]
  140001456:  test   eax,eax
  140001458:  cmovs  eax,edx            ; hp<0 时 eax=0，无分支
  14000145b:  mov    [rcx],eax
  14000145d:  ret
```

18 条 → 7 条。两个必须习惯的变化：

1. 参数不落栈，直接用 `rcx` / `edx`
2. `if` 分支变成 `cmovs`，源码结构被抹掉

**结论：优化会删掉判断依据，必须结合动态调试。**

## 调试器验证

断点下在**函数体第一行**（不能是入口，序言没执行时参数位置不准）：

```
p = 0x5ffea0
dmg = 30
$1 = {hp = 100, max_hp = 100, x = 1.5, y = 2.5, z = 3.5, name = "hero", flags = 0}

$2 = 0x64          ← *(int*)p        = 100 = hp
$3 = 0x64          ← *(int*)(p+4)    = 100 = max_hp
$4 = 0x3fc00000    ← *(float*)(p+8)  = 1.5 = x
$5 = 0x40200000    ← *(float*)(p+12) = 2.5 = y
```

`0x3fc00000` 就是 **1.5 的 IEEE 754 表示**。逆向里一片「乱码数字」，很多其实是浮点坐标。

## 三条要背下来的规则

1. **参数传递**：Windows x64 前 4 个参数依次在 `rcx`、`rdx`、`r8`、`r9`，第 5 个起走栈
2. **栈帧偏移**：`[rbp+0x08]` 是返回地址，`[rbp+0x10]` 是第 1 个参数的 home space（影子空间）
3. **方括号里的数字就是结构体字段偏移**：`[rcx+0x24]` = 读 `flags`
