# 为什么 `p_ptr[1]` 是 +4 字节而不是 +1

## 我的回答（第一反应）

因为 `p_ptr` 的地址类型被推断为 `int *`。

## 更完整的回答

你的方向对了**一半**，但漏了最关键的一环。

「`p_ptr` 被推断为 `int *`」回答的是：**Ghidra 为什么写成 `p_ptr[1]` 这种形式**。

它没回答：**为什么 `[1]` 就是 4 个字节**。

这两个是不同的问题，因果链要拆成两段。

### 第一段：C 语言的下标就是指针加法

标准规定（不是编译器实现细节，是语言规则）：

```c
p[i]   等价于   *(p + i)
```

而**指针加法前进的单位不是字节，是 `sizeof(*p)` 个字节**：

```c
int *p;
p + 1;    // 地址前进 4 字节，因为 sizeof(int) == 4
```

这就是 `[1]` → `+4` 的**真正原因**。它跟 Ghidra 无关，是 C 语言本身的语义。

### 第二段：Ghidra 的类型推断决定了「怎么写」

Ghidra 只观察到：

```
[RAX]      被当作 4 字节读
[RAX + 4]  也被当作 4 字节读
```

于是推断「指向 int 数组」，把第 0、第 1 个元素写成 `*p_ptr` 和 `p_ptr[1]`。

**推断在字节层面是对的，语义层面是错的**——它不知道这是 `Player` 结构体的两个字段。

### 合起来

```
汇编 [RAX + 0x4]
   ↓  Ghidra 推断类型为 int*
C 代码 p_ptr[1]
   ↓  指针加法规则：1 * sizeof(int) = 4
字节偏移 +4
   ↓  对照结构体布局
p->max_hp
```

### 一个表看清：同一个偏移，不同写法

| 表达式 | 元素大小 | 实际字节偏移 |
|---|---:|---:|
| `((char *)p)[1]` | 1 | **+1** |
| `((short *)p)[1]` | 2 | **+2** |
| `((int *)p)[1]` | 4 | **+4** |
| `((Player *)p)[1]` | 40 | **+40 = 0x28** |

> `sizeof(Player)` 正好 40，见 [docs/01-memory-layout.md](../docs/01-memory-layout.md)。

### 三种完全等价的写法

```c
p->max_hp                    // 结构体成员（最可读）
*(int *)((char *)p + 4)      // 字节偏移（最原始）
((int *)p)[1]                // 整型数组下标（Ghidra 推测）
```

**逆向的工作就是把后两种还原成第一种。**

### 如果类型猜错会怎样

把 `Player *` 当成 `int *`，`p[1]` 算出来是 +4（对），但你已经不知道它是 `max_hp`。
反过来，如果把 `int *` 当成 `Player *`，`p[1]` 会算成 **+40**，直接读到结构体外面——偏移全错，分析报废。

**所以「恢复类型」和「恢复偏移」同等重要。**

### 怎么在 Ghidra 里修

1. 右键 `p_ptr` → `Retype Variable` → 输入 `Player *`
2. 按 `F5` 重新反编译

`p_ptr[1]` 会自动变成 `p->max_hp`，`*p_ptr` 变成 `p->hp`。

> 前提是项目里已经有 `Player` 这个类型。带 `-g` 编译时 DWARF 会带进来；没有调试符号就得在 `Data Type Manager` 里手工建。

## 结论

1. `p[1]` 的字节偏移 = `sizeof(*p)`，不是 1。
2. 「Ghidra 推断成 int*」只解释了写法，不解释字节数。
3. 看到数组下标，先确认 Ghidra 推测的类型对不对。
4. **恢复类型 = 让偏移变成字段名 = 让代码可读。**
